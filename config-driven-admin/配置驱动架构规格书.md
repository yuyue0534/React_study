# 配置驱动架构 · 规格书

版本：v0.2（对应 iframe / slider / custom 补全后的实现）

本规格书是字段级参考，描述每一层配置的结构、类型和约束。使用教程见
《新手使用指南》。

---

## 1. 顶层结构

```typescript
interface DSLConfig {
  model: string;      // 模型标识，如 'dashboard'
  name: string;        // 系统名称，显示在左侧导航顶部
  menu: MenuNode[];     // 菜单树，见第 2 节
}
```

## 2. 菜单节点 MenuNode

```typescript
interface MenuNode {
  key: string;                    // 必填。唯一标识，用于路由、递归定位、project 合并
  name: string;                   // 必填。菜单显示名称
  menuType: 'module' | 'group';   // 必填。module=可渲染页面；group=纯分组目录
  moduleType?: 'schema' | 'iframe' | 'custom' | 'slider'; // menuType 为 module 时必填
  subMenu?: MenuNode[];           // menuType 为 group 时必填，子节点
  schemaConfig?: SchemaConfig;    // moduleType: 'schema' 时必填
  iframeConfig?: IframeConfig;    // moduleType: 'iframe' 时必填
  customConfig?: CustomConfig;    // moduleType: 'custom' 时必填
  sliderConfig?: SliderConfig;    // moduleType: 'slider' 时必填
  _deleted?: boolean;             // 仅在 project 配置里使用，标记删除该 key 对应的 model 节点
}
```

**约束**：
- `menuType: 'module'` 时，`moduleType` 必填，且对应的 `xxxConfig` 必填。
- `menuType: 'group'` 时，不应设置 `moduleType`，`subMenu` 必填，可以为空数组。
- 同一层级内 `key` 不能重复。
- `key` 一旦发布不建议改名，project 继承 model 的合并、以及前端路由都依赖它保持稳定。

## 3. schemaConfig（moduleType: 'schema'）

```typescript
interface SchemaConfig {
  api: string;                     // 必填。RESTful 基础路径，如 '/api/proj/product'
  schema: {
    type: 'object';
    properties: Record<string, FieldDef>;  // 必填，至少一个字段
  };
  tableConfig: {
    headerButtons: ButtonDef[];    // 表格头部按钮，通常放"新增"
    rowButtons: ButtonDef[];       // 每行的操作按钮，通常放"修改"/"删除"
  };
}
```

### 3.1 FieldDef

```typescript
interface FieldDef {
  type: 'string' | 'number' | 'boolean';  // 必填，决定表单输入控件和值类型转换
  label: string;                          // 必填，字段中文名，三个视图共用
  tableOption?: TableOption;              // 挂了才在表格里显示这一列
  searchOption?: SearchOption;            // 挂了才在搜索栏出现
  formOption?: FormOption;                // 挂了才在新增/编辑表单出现
}
```

> **核心规则**：`buildDtoSchema(schema, comName)` 只挑出配了 `${comName}Option`
> 的字段。三个 Option 相互独立、可以任意组合——一个字段完全可以只在表格显示、
> 不能搜索、不能编辑（比如 `create_time` 通常这么配）。

### 3.2 TableOption

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `width` | number | 否 | 列宽（px） |
| `prefix` | string | 否 | 显示前缀，如 `'$'` |
| `show-overflow-tooltip` | boolean | 否 | 内容超长时是否 tooltip 展示全文 |

### 3.3 SearchOption

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `comType` | `'input' \| 'select' \| 'dynamicSelect' \| 'dateRange'` | 是 | 搜索控件类型 |
| `placeholder` | string | 否 | 输入框占位文字 |
| `enumList` | `{label:string, value:any}[]` | `comType: 'select'` 时必填 | 下拉选项 |
| `api` | string | `comType: 'dynamicSelect'` 时必填 | 远程下拉数据源 |

### 3.4 FormOption

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `comType` | `'input' \| 'select' \| 'textarea'` | 是 | 表单控件类型 |
| `required` | boolean | 否，默认 false | 是否必填校验 |
| `enumList` | `{label:string, value:any}[]` | `comType: 'select'` 时必填 | 下拉选项 |

> 注：`formOption` 是在原始 DSL 基础上做的延伸，用于让新增/编辑表单也走
> `buildDtoSchema` 同一套拆分逻辑，保持三视图架构一致。

### 3.5 ButtonDef

```typescript
interface ButtonDef {
  label: string;                              // 必填，按钮文字
  eventKey: string;                            // 必填，见第 5 节事件系统
  type?: 'primary' | 'warning' | 'danger' | 'default';  // 按钮视觉样式
  eventOption?: {
    params?: Record<string, string | number>;  // 传给事件处理函数的参数
  };
}
```

`eventOption.params` 里的值支持一种占位符协议：

```
"字段名": "schema::字段名"
```

表示"从当前行数据里取该字段的值"。解析这个协议的函数是 `resolveParams`，
如果未来要支持更多来源，可以扩展前缀协议，比如 `route::id`（取路由参数）、
`store::userId`（取全局状态），只要在 `resolveParams` 里加对应分支。

## 4. iframeConfig（moduleType: 'iframe'）

```typescript
interface IframeConfig {
  path: string;   // 必填。要嵌入的外部页面地址
}
```

无其他字段。渲染时直接把 `path` 交给 `<iframe src={path} />`。

## 5. customConfig（moduleType: 'custom'）

```typescript
interface CustomConfig {
  path: string;   // 必填。自定义路由地址，DSL 解析器只登记这个入口
}
```

`custom` 类型不参与 DSL 的字段级渲染，具体页面组件由业务方自行实现并挂载到
`path` 对应的路由上。适用于"配置驱动覆盖不到的场景"。

## 6. sliderConfig（moduleType: 'slider'）

```typescript
interface SliderConfig {
  menu: MenuNode[];  // 必填。子菜单树，节点结构与顶层 MenuNode 完全一致
}
```

`sliderConfig.menu` 里的节点可以是任意 `moduleType`（包括再嵌一层
`slider`），也可以是 `menuType: 'group'` 做分组。渲染时侧边栏选中某个叶子
节点后，交给同一个 `ModuleRenderer` 分发，与顶层渲染逻辑完全复用。

## 7. 事件系统

### 7.1 内置 eventKey

| eventKey | 触发行为 |
|---|---|
| `showComponent` | 打开新增/编辑弹窗。行按钮触发时带当前行数据（编辑），头部按钮触发时不带（新增） |
| `remove` | 调用 `DELETE {api}`，用 `eventOption.params` 解析出的参数删除对应记录 |

### 7.2 扩展新的 eventKey

往事件注册表里加一条即可，不需要改解析器或按钮渲染逻辑：

```javascript
const eventHandlers = {
  showComponent: (button, ctx) => { /* ... */ },
  remove: (button, ctx) => { /* ... */ },
  export: (button, ctx) => {           // 新增一个"导出"动作
    const params = resolveParams(button.eventOption?.params, ctx.rowData);
    ctx.api.download(`${ctx.schemaConfig.api}/export`, params);
  },
};
```

`ctx` 对象约定包含：`rowData`（当前行数据，头部按钮为 null）、`log`（日志
函数）、`openModal`、`removeRow`，可按需扩展更多方法。

## 8. moduleType 注册表（可扩展点）

```typescript
const moduleRegistry: Record<string, React.ComponentType<{ node: MenuNode; log: LogFn }>> = {
  schema: SchemaView,
  iframe: IframeView,
  custom: CustomView,
  slider: SliderView,
};
```

新增一种 `moduleType`（比如看板视图 `kanban`）时：

1. 定义对应的 `kanbanConfig` 结构
2. 写一个 `KanbanView` 组件，接收 `{ node, log }` props
3. 往 `moduleRegistry` 里加一行 `kanban: KanbanView`

不需要改动 `menuTreeToRoutes`、`findMenuItem`、`ModuleRenderer` 或任何已有模块。

## 9. project 继承 model 的合并规则

```typescript
function projectExtendModel(model: DSLConfig, project: Partial<DSLConfig>): DSLConfig
```

作用于 `menu` 及其任意深度的子数组（`subMenu`、`sliderConfig.menu`）：

| 情形 | 行为 |
|---|---|
| project 节点与 model 节点 `key` 相同 | 递归合并（project 覆盖同名字段，未提及字段保留 model 的值） |
| project 节点 `key` 在 model 里不存在 | 追加到结果数组末尾 |
| model 节点 `key` 在 project 里未出现 | 原样保留 |
| project 节点带 `_deleted: true` | 从合并结果里移除该 key 对应的 model 节点 |

**已知限制**：合并按数组元素的 `key` 字段识别对应关系。像
`tableConfig.headerButtons` 这类数组，元素通常没有 `key`，project 提供的项
会被追加而非替换整个数组。如果业务上需要"整体覆盖某个无 key 数组"，需要
给这类数组元素也约定 `key`，或者为该数组单独写合并规则。

## 10. 建议的配置校验时机

| 校验类型 | 建议时机 | 说明 |
|---|---|---|
| 结构校验（字段类型、必填项） | 应用启动 / 配置加载时 | 用 JSON Schema 或 zod 等运行时校验库，报错要带具体路径 |
| 语义校验（`moduleType` 与 `xxxConfig` 联动） | 结构校验之后 | 普通 JSON Schema 表达能力有限，建议单独写校验函数 |
| project/model 合并结果校验 | 合并完成后，渲染之前 | 确保合并结果本身仍然满足结构+语义校验，防止 project 引入非法配置 |
| lint（key 重复、命名规范） | CI / 提交前 | 脚本化检查，不依赖运行时 |
